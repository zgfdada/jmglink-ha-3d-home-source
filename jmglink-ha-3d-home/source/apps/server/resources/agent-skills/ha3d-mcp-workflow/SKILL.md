# Home3D MCP 使用规范

> 版本：v1.1.2。本 Skill 规范应用层操作，不扩大用户授权。

## 一、先确认连接与能力

开始处理需求前，确认 MCP 能正常连接，并读取当前项目、服务状态、可用能力和权限范围。连接异常时，先引导用户检查服务运行、连接地址、MCP 开关和认证配置；不要在未连接的情况下假定项目状态或声称已完成修改。

查询与排障可参考项目说明：

- [项目 README（GitHub）](https://github.com/zgfdada/jmglink-ha-3d-home-source/blob/main/README.md)
- [项目 Wiki（GitHub）](https://github.com/zgfdada/jmglink-ha-3d-home-source/wiki)

GitHub 为当前项目文档来源。Wiki 如尚未开放或跳转到仓库首页，先查 README 和仓库 docs，不假定 Wiki 内容已存在。

连接正常后，应先了解当前能读取、修改和控制哪些内容。将用户需求与权限及工具能力对照；涉及范围以外的 HA、Node-RED 或其他操作时，说明缺少什么、为什么需要，并询问用户是否开启。不能把“连接成功”当作完整权限，也不能自行扩大权限或换入口绕过限制。

### MCP 优先，减少前端操作

先读取 `system.capabilities` 与工具列表；涉及设备开发中心时，再读取 `home3d.schemas.get`。能够通过 MCP 完成的读取、配置、资源复用、实体映射、动画规则、批量摆放、计划应用和回读，尽量直接使用 MCP。不要为了熟悉界面、参数不清楚或已有页面打开，就改用大量点击。先查工具说明与当前配置，按修订号生成计划，校验后以唯一幂等键应用。

只有当前 MCP 确实缺少对应能力、明确不支持该模型结构，或需要实际画面／多角度验收时，才使用前端；先说明缺少的具体接口及前端操作范围。遵循用户指定的浏览器与已有授权，不擅自接管 Chrome。前端完成缺口后回到 MCP 继续可支持的操作。工具不可用时如实说明，不以未声明的底层接口或直接修改实例文件绕过。

设备与资源操作入口及字段见 [MCP 操作速查](references/mcp-tools.md)。接口版本可能不同，实际可用工具与权限以当前服务返回为准；不因本说明列出工具就宣称服务已升级。

## 二、限定在应用配置层操作

通过 MCP 调整应用中的配置、资源、模型、摆放、设备绑定、动画和业务流程，不修改 Home3D 或集成的源代码、底层实现和系统环境。

遇到当前能力不能实现的需求，应说明限制和可行方案，与用户确认后续处理。不得为了完成配置任务擅自改代码、部署补丁或增加底层接口。

Node-RED 中的业务流程属于本规范允许的应用层逻辑配置；涉及 Function 等节点时仍须符合当前授权。

## 三、先确认效果，再修改界面与模型

涉及侧边栏、控件、家居或设备模型等视觉调整时，先遵循当前主题和整体风格，再确认用户期望的效果。

涉及模型、摆放或特效时，先了解用户已有的参考效果图／场景图；已有场景和需求足够明确时，可直接据此制作方案预览。确认材料必须是真正可看的场景效果图、渲染预览，或能够打开观看的 HTML 场景／交互预览。Markdown／Mermaid 流程图、ASCII 图、文字布局、参数表只能辅助说明，不能作为视觉效果确认材料，也不能用用户对文字方案的认可代替对实际画面的确认。

预览应尽量以当前家庭场景及现有模型为基础，展示本次修改后的实际空间关系和整体风格。至少看得清相关位置、比例尺寸、朝向、安装与支撑方式、材质和配色；需要时补充俯视或侧视图。单个模型或音波的孤立示意只能确认该局部，不能代替整套设备摆放或完整场景的确认。HTML 预览应实际打开并检查渲染，向用户提供可访问入口和截图；不能只交付 HTML 源码、代码块或文件名。

涉及动画时，优先提供可播放的 HTML、动图、视频或渲染预览，展示触发后的循环、扩散方向、起点、范围、速度及停止表现。静态场景效果图可辅以关键帧和必要标注，但不能只靠文字解释动画。使用概念渲染、合成图或独立 HTML 演示时，明确标记为待确认方案，与当前应用的实渲染及实施后验收区分；不得将推演画面描述为已经落地的效果。

必须在用户看过并确认上述视觉预览后，才能创建／修改正式模型、摆放或特效。为制作确认材料，可在内存、独立 HTML 或隔离的预览环境中制作视觉草案，不覆盖正式资源、场景或未发布草稿，不触发真实设备，也不因此扩大访问权限。已有确认的同一视觉方案可以沿用；用户在此基础上明确要求的局部调整可直接实施，整体方案发生实质变化时重新提供视觉预览确认。

确认的是整体效果，包括布局、尺寸、材质、配色和交互；不能只改一个内部按钮或展示单件音箱，就把它当作整张卡片或整套家庭影音场景的确认。当前工具无法提供合格视觉预览时，说明具体缺口，不能退回用流程图或文字概念宣称已完成效果确认。

## 四、先明确空间位置，再摆放

设备或家居摆放前，明确目标位置、朝向、高度、尺寸与安装方式。优先请用户提供场景图片并框选位置；现有图片和描述已能准确定位时可直接使用，仍有歧义则补充确认，不自行猜测。

摆放要遵循基本物理规则：落地、柜面、贴墙或吊装应有相应支撑，不能无依据悬空、穿墙、嵌入柜体或相互重叠。位置、比例与周边空间应协调，不能只看单个坐标数值是否合理。

## 五、模型必须进入资源体系

### 先复用，再由用户决定修改或新建

开始建模前，先通过 MCP 检索现有模型库并检查预览、尺寸、材质、结构和作用部件，优先直接复用当前模型；同型设备通过多个独立实例共享一个资源，不复制出多份相同模型。现有模型不合适时，先向用户说明具体差异和影响，明确申请由用户选择“修改已有模型”还是“新建单件模型”，并提供对应图示。确认前不得自行改模型文件、新建替代模型或导入临时整套模型。修改共享模型前列出受影响引用，不能顺带改变其他设备。

### 成套设备由独立单件组合

家庭影音、灯组等成套设备不能合并建成一个难以拆调的整套模型。以家庭影音为例，主音箱、中置、环绕、天空声道和低音炮按不同外形分别入库；左右同型音箱复用一个模型资源，但作为独立场景实例分别摆放。保持每件设备的位置、朝向、尺寸、实体关联和部件动效可独立调整，通过情景／业务逻辑组合成 2.1、5.1.2 等系统。系统编组可以共用运行实体或情景，不要求伪造每个声道的真实硬件实体。沿用已存在的单件资源和摆放，不因声道升级就整体重建。

创建模型时，明确归类为“家居”或“设备”，至少属于其中一类，并在 3D 资源库中可找到、可预览、可再次使用。不能只出现在主页场景中，而资源库没有对应项目。

根据用途完成资源、场景实例及必要绑定。家居强调摆放与外观；设备还应具备相应实体、控制和状态表现。已有家居转为设备时，保留确认的位置和外观，处理重复实例与旧引用。

## 六、以实体状态驱动设备动画

需要设备随传感器、实体状态或属性变化时，通过设备开发中心配置动画效果与绑定。先查看内置及已有动画是否适配；不能满足需求时，在设备开发中心创建新的动画效果，再绑定到对应设备及状态条件。

动画应适配实际模型、作用部件和业务含义，明确触发、变化、停止及恢复行为。不能仅用浏览器临时演示开关替代实体联动，也不能直接改场景渲染代码代替设备动画配置。

通过 MCP 读取模型部件路径和原始名称，中文标签只用于显示，不作为部件身份。复用动效资源时保存完整规则快照；修改前保留其他规则。使用 MCP 条件模拟检查运行、停止与不可用分支；条件匹配、语法校验不等同于 JavaScript 动效实际运行或真实画面验收。静态部件树无法确认时明确报告，不能猜测路径。

当前 HA 实体集合中没有需要的实体时，在获得相应权限的范围内创建虚拟实体，并完成用途说明和绑定。虚拟实体用于模拟或业务控制，不能声称是真实硬件已经接入；涉及真实物理量时不能伪造传感器数据。现有能力无法创建所需类型时，说明限制并确认替代方案。

### 运行浮窗与部件动画分开配置

需要状态驱动音波等部件动画，不等于需要在全屋场景显示运行浮窗。仅为动画绑定实体时，使用能力映射和 `appearance.partMotionRules`；不要为了满足诊断或发布检查而擅自添加运行浮窗或通用运行联动。诊断提示缺少运行浮窗时，按用户实际需求处理，不能以消除提示为由增加界面元素。

用户要求取消运行浮窗时，既要检查 `runtimeDisplay`，也要检查 `appearance.animation` 和模型的 `runtimeEffect`。当前实现中，仅清空 `runtimeDisplay` 仍可能通过通用运行联动生成浮窗，并回退为“洗衣中”等不适合该设备的默认文案。保留用户需要的能力映射、部件动效规则及资源快照，只清理导致浮窗的配置；具体字段与限制见 [运行浮窗取消与回退排查](references/mcp-tools.md#运行浮窗取消与回退排查)。

取消后先回读确认部件规则未变，再刷新全屋页面，检查设备运行时浮窗确实消失且动画仍正常。不能只凭 `runtimeDisplay` 已清空、计划已应用或条件模拟通过就宣称完成；不为验收擅自触发灯光、窗帘等真实动作。

## 七、控制逻辑优先使用 Node-RED

控制逻辑和情景编排默认在 Node-RED 中开发。只有用户明确指定 HA 自带功能、其他集成或其他实现方式时，才改用对应方式；Node-RED 不可用时先说明，不擅自切换实现平台。

新增业务逻辑应具备清楚的命名、备注与标签：说明用途、触发条件、控制对象、执行顺序、关键限制及异常处理。备注应能让用户在编辑器中理解和维护流程，不依赖聊天记录。

优先复用已有业务模式，避免新逻辑与现有自动控制相互争抢。明确触发入口、流程、设备与实体之间的关系，并将入口放到用户指定的位置。部署完成后确认入口真实显示、目标正确、流程已生效。

## 八、完成配置后进行整体验收

验收应围绕用户的完整需求，而非只确认某一个节点、接口或画面成功。

- 从多个角度和方向观察模型，确认位置、尺寸、朝向、高度、支撑、遮挡与空间关系符合正常逻辑。
- 检查资源库、场景、设备、实体、动画与控制入口是否对应完整，没有遗漏、重复或失效引用。
- 验证状态和属性变化能驱动预期动画与控制逻辑，并检查关闭、恢复、不可用及重复触发时的表现。
- 界面调整要检查主题一致性、内容可读性、整体尺寸和相关设备端／停靠布局，不能只验收单张静态图。

明确区分“配置已保存”“流程已部署”“界面已确认”和“实机已验证”。设备不可用或权限不足时，报告具体未完成项，不用局部成功替代整体完成。截图应能看清本次修改对象与相关空间关系。

## 九、操作完整性与交付规则

以下规则与前述流程共同执行：

- **保护已有成果**：修改前读取当前配置，保留无关对象和未发布草稿；应用前核对变更范围与版本，必要时准备可恢复的配置快照。
- **异常后先核实**：失败、超时或结果不明时，先检查实际状态，再决定重试，避免重复创建资源或重复控制设备。
- **创建与执行分开说明**：明确本次是建立配置还是立即触发情景。测试涉及真实灯光、窗帘等动作时，按用户授权执行，并说明测试后的最终状态；是否默认实测、是否恢复原状态由用户确定。
- **保持改动边界**：不顺带调整透明度、相机、其他设备或全局主题。已确认的用户选择持续有效，后续纠正应修复到实际结果。
- **如实交付**：简要说明完成内容、使用位置、验证结果及仍需处理的问题，不把演示、模拟或部分完成说成真实联动已全部成功。

本 Skill 的安装、更新或发布须按用户指示执行；规范内容本身不授权对现网进行新的配置修改或设备控制。
